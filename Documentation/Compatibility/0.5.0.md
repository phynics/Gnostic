# Gnostic 0.5.0 compatibility

**Status: in development (unreleased).** Gnostic 0.5.0 is the first supported
line and the source- and wire-breaking minor release after [0.4.2](0.4.2.md).
This declaration records the target contract. The final release declaration
will be checked against the built products and the migration tool before the
0.5.0 tag.

The binding architecture decision is [ADR 0021](../Architecture/ADRs/0021-gnostic-v0-5-architecture-reconciliation.md).
The release gates are tracked by [#551](https://github.com/phynics/Gnostic/issues/551)
and [#602](https://github.com/phynics/Gnostic/issues/602).

## Package and protocol

- Package version: `0.5.0`.
- Protocol major: `3`. This is one breaking increment from protocol major 2.
  A 0.4.2 peer does not interoperate with a 0.5.0 peer.
- The v0.5 operator configuration uses the Runtime, Timeline, Session, and
  Project model. A pre-v0.5 manifest v2 file is an input to the explicit
  migration tool in #642. Schema-v1 migration remains removed under ADR 0003.
- Gnostic accepts ACP v2 only. ACP v1 clients and Runtimes are unsupported.
- ACP v2 support is an opt-in preview behind explicit configuration. It is
  outside the 0.5.x stability promise until ACP v2 stabilizes.
- **0.5.x ACP prompts are text only** (owner decision D33 on #551, issue #732).
  `gnostic acp` rejects a prompt that holds a non-text content block (image,
  audio, resource, or resource link) with JSON-RPC invalid params, and it rejects
  an empty prompt. It joins several text blocks, in order and with no separator,
  into one prompt. A client that needs another content type waits for
  [#731](https://github.com/phynics/Gnostic/issues/731), which tracks multimedia
  prompt support. This narrows ADR 0018 §4 for 0.5.x, and the ADRs carry the
  amendment.

## Stable products

The stable Swift products planned for 0.5.0 are `GnosticProtocol` and
`GnosticClient`. `make verify` runs `make api-check`, which fails on any
unreviewed change to their public API against a baseline the compiler wrote
([`API/`](API/README.md), #676). The 0.4.2 to 0.5.0 differences are recorded,
without gating, in [the API diff](0.4.2-to-0.5.0-api-diff.md). ACP v2 transport
remains preview even when Gnostic's own protocol and consumer clients are
stable.
`GnosticACPWire` is a separate preview product used by ACP Runtime executables.
Its symbols do not enter the 0.5.x stability promise.

### Stable surface names

`GnosticProtocol` and `GnosticClient` name no Ascendant, and no `GnosticCore`
type appears in a `GnosticClient` public signature (owner decisions D13, D17,
D18, and D19 on #551; issue #675). `StableSurfaceFitnessTests` scans both
targets and fails on a declaration that says Ascendant or on a `GnosticCore`
type in a public client signature.

- **Turn types are `Turn*`.** The types that were `Ascendant*` and `Timeline*`
  Turn names are `Turn*`, and they live in `GnosticProtocol`.
- **The Runtime instance is the only identity projection.**
  `GnosticAscendantObject` and the `me.atkn.gnostic.Ascendant` object type are
  deleted. A Node advertises a `GnosticRuntimeInstanceObject` for each
  configured instance as soon as it starts, so a client can address the
  instance before its Runtime connects. After the Runtime answers ACP
  `initialize`, the advertisement carries the version, launch fingerprint, and
  capabilities from that answer.
- **`GnosticProtocol` no longer re-exports ACP names.** The 87 `ACP*`
  typealiases are removed. Code that names an ACP wire type imports
  `GnosticACPWire`, which is a preview product outside the 0.5.x promise.
  **No stable signature names an ACP type.** No ACP-typed declaration remains in the
  two stable products (owner decision D27 on #551, #716):
  `GnosticRuntimeInstanceObject.rawCapabilities` is
  `[String: GnosticJSONValue]`, `TurnTerminalOutcome.from(stopReason:)` is
  package-only, and `TurnSessionUpdate` moved to `GnosticCore`, because
  `GnosticCore`'s public journal payload carries it. The journal still encodes
  `TurnSessionUpdate` exactly as before. `TurnSessionUpdate.update` stays public
  in `GnosticCore` (owner decision D35 on #551): it is a variant of D27's
  "package-only", because the public journal payload needs the value. It names an
  ACP type. `GnosticCore` is outside the 0.5.x stability promise, and no stable
  signature names an ACP type. `StableSurfaceFitnessTests` fails if
  the baseline names a `GnosticACPWire` type.
- **Deliberate exceptions.** Architecture exception `GNO-EXC-0001`
  ([#721](https://github.com/phynics/Gnostic/issues/721)) no longer covers a
  stable product. The Coaty-era object model (`CoatyObject`, `CoatyUUID`,
  `CoreType`) and the `Gnostic*Object` transport classes moved to `GnosticCore`
  (owner decision D29, [#717](https://github.com/phynics/Gnostic/issues/717)),
  which is not a stable product. The exception now scopes six `GnosticCore`
  files. The name rule has no exception: decision D20 keeps the CLI `ascendant`
  commands and `NodeManifest.Ascendant` (the `ascendants` manifest key) until
  after rc.1, and neither is in a stable product. The reference-type rule has
  five listed exceptions, the `@MainActor` clients (see [Immutable
  snapshots](#immutable-snapshots-d29)).

#### Trimmed public API (R2: D27, D28, D30)

[#716](https://github.com/phynics/Gnostic/issues/716) applies the owner's R2
decisions to `GnosticProtocol` and `GnosticClient`. The host and Core targets
keep the removed symbols, either with `package` access or as public types of
`GnosticCore`, so no behavior moves. The baseline in [`API/`](API/README.md) records the removal.

- **Wire plumbing is package-only.** `GnosticProtocol.decodeMajor`,
  `boundedStatusCode`, `failureMessage`, `validatePayload`;
  `GnosticWirePayload.encode`, `validateEvent`, `prefix`, `boundedLabel`,
  `boundedIdentifier`, `boundedWorkspaceIDs`; `TurnPermissionResponse.targeted(to:)`.
  The public limits
  (`GnosticWirePayload.maximum*`), the compatibility checks
  (`GnosticProtocol.currentMajor`, `isCompatible`, `validate`), the
  `GnosticWirePayload.Error` cases, `canonicalTurnMessage`, and
  `canonicalClientTurnID` stay public.
- **Core records moved to `GnosticCore`.** `RuntimeInstanceIdentity`,
  `RuntimeInstanceCapabilities`, `RuntimeInstanceTimeline`, `GnosticPublicFailure`,
  and `TurnError` are the Core's own types. `GnosticCore` is not a stable
  product. A consumer reads `RuntimeInstanceSnapshot` and `TimelineSnapshot`
  (D29, below).
  `GnosticTimelineObject` has the memberwise
  `init(id:title:attachedWorkspaceIDs:runtimeInstanceID:isArchived:isPrivate:createdAt:updatedAt:nodeID:protocolMajor:)`,
  and `GnosticCore` keeps `init(timeline:)` as an extension. Both are in
  `GnosticCore` since #717.
- **Diagnostics drop four fields.** `RuntimeInstanceDiagnostics` no longer
  carries `privateTimelineID`, `primaryWorkspaceID`, `backendKind`, or
  `backendVersion`. `gnostic inspect` text drops the `backend=` and
  `privateTimeline=` lines for a Runtime instance.
- **`GnosticRuntimeInstanceObject.runtimeID` is `runtimeInstanceID`.** The
  encoded key stays `runtimeID`.
- **`GnosticWorkspaceLocation.runtimeThread` is removed.** No Node, Runtime, or
  test produces the value. It names the thread Workspace of the in-process
  backends that 0.5.0 removed. After rc.1 a case cannot leave a frozen enum, so
  rc.1 is the last release that can drop it at no cost. The cases are now
  `runtime` and `attached`.
- **Workspace arguments and schemas are `GnosticJSONValue`.** Tool invocation
  arguments (`GnosticWorkspaceClient.invoke`) and tool parameter schemas
  (`GnosticWorkspaceToolDefinition`, `GnosticWorkspaceObject`,
  `GnosticWorkspaceToolObject`) no longer use `ManifestJSONValue`, which held
  every number as a `Double` and so rounded integers above 2^53.
  `GnosticJSONValue` keeps `Int64` and `UInt64` values exact.
  `MultiplexedWorkspaceProviderTests` sends an invocation argument of 2^53 + 1
  through the wire encoding, and `WorkspaceMCPGatewayConformanceTests` checks
  the same value from an MCP call.
  `ManifestJSONValue` moved to `GnosticCore` and is manifest vocabulary only.
  Its cases are `.bool` and `.object`; `GnosticJSONValue` names them `.boolean`
  and `.dictionary`.
- **`GnosticRawWireEvent` is supported.** Its signatures are part of the 0.5.x
  promise. Only delivery is best effort: an observer that falls behind loses the
  oldest events, and nothing persists or replays them.

##### Enum policy

Small domain enums keep their cases through 0.5.x (owner decision D30). A
*frozen* enum gains and loses no case in a 0.5.x release, and its decoder rejects
a value it does not know. Adding a case needs a new protocol major or a new minor
release. An *open* value is a string on the wire. The enum for it only names the
values this build knows, a new minor release may add cases, and a consumer
handles an unknown value with a `default` branch.

| Enum | Policy | Cases |
| --- | --- | --- |
| `GnosticRuntimeInstanceHealth` | Frozen | `healthy`, `failed`, `unknown` |
| `GnosticWorkspaceTrustLevel` | Frozen | `full`, `restricted`, `readOnly` |
| `GnosticWorkspaceStatus` | Frozen | `active`, `missing`, `unknown` |
| `GnosticWorkspaceEffectiveStatus` | Frozen | `available`, `unavailable`, `unsupported` |
| `GnosticWorkspaceLocation` | Frozen | `runtime`, `attached` |
| `TurnTerminalOutcome` | Frozen | `completed`, `endedUnspecified`, `cancelled`, `failed`, `insertionUnknown`, `unavailable` |
| `DiagnosticsTimelineSessionState` | Frozen | `live`, `resumable`, `lost`, `ambiguous` |
| `DiagnosticsTimelineJournalState` | Frozen | `writable`, `quarantined` |
| `GnosticRawWireEventKind` | Frozen | `advertise`, `deadvertise`, `discover`, `resolve`, `query`, `retrieve`, `update`, `complete`, `call`, `returnEvent`, `channel` |
| `NetworkCatalogChange` | Frozen | `advertised`, `deadvertised`, `providerEvicted` |
| `WorkspaceAttachmentStatus` | Frozen | `unavailable`, `malformed`, `ambiguous`, `unsupported`, `available` |
| `NetworkDynamicValue` | Frozen | `null`, `bool`, `number`, `integer`, `unsignedInteger`, `string`, `array`, `object` |
| `Project.Kind` | Frozen | `local`, `scratch` |
| `TurnUpdateKind` | Open | Names the values of `TurnUpdate.kind`: `assistant_text`, `assistant_text_snapshot`, `thought`, `plan`, `tool_call`, `tool_state`, `permission_state`, `completion`, `cancellation`, `error`. `thought` and `plan` joined before rc.1 (D32) |
| `TurnToolStatus` | Open | Names the values of `TurnToolState.status` |
| `TurnPermissionStatus` | Open | Names the values of `TurnPermissionState.status` |

Other open values have no enum: failure `reasonCode` strings, `GnosticObjectType`
identifiers, and `TurnUpdate.reasonCode`. The eight error enums
(`GnosticTurnClientError`, `GnosticTimelineClientError`,
`GnosticDiagnosticsClientError`, `GnosticWorkspaceClientError`,
`GnosticConsumerSessionError`, `GnosticProtocolError`, `ProjectValidationError`,
`GnosticWirePayload.Error`) are not frozen through 0.5.x (owner decision D34).
A consumer matches them with a `default` branch. The compiler does not enforce
that branch: a switch that names every case compiles today, and a case added in a
later 0.5.x release breaks that switch when the host rebuilds. Hosts should use
`default`. `GnosticJSONValue` follows the JSON data model and does not change.
It is not listed in the table, and the fitness test exempts it by name.

`StableSurfaceFitnessTests` reads the two API baselines. It fails when a public
enum with cases is in neither the table nor the error list above. It also fails
when the cases of a Frozen enum in the baseline differ from the cases in its row.
An enum with no cases (`GnosticObjectType`, `GnosticProtocol`,
`GnosticWirePayload`) is a namespace and is exempt.

#### Immutable snapshots (D29)

[#717](https://github.com/phynics/Gnostic/issues/717) applies owner decision
D29 on #551. The public projection classes were mutable, inherited public
properties from `CoatyObject`, and were `@unchecked Sendable`, so the API
promised safe transfer between actors that nothing enforced. No mutable
reference type and no `@unchecked Sendable` type is in a public signature of
`GnosticProtocol` or `GnosticClient`. A consumer reads immutable `Sendable`
value snapshots. Every property is a `let` (or computed), so a value crosses
actors without synchronization.

A snapshot reaches a consumer through `NetworkCatalogEntry`, which
`GnosticConsumerSession.networkObjects`, `object(id:providerID:)`, and
`catalogUpdates()` return:

| Before | After | Consumer migration |
| --- | --- | --- |
| `GnosticRuntimeInstanceObject` (class; decoded from an entry's payload) | `RuntimeInstanceSnapshot`, from `NetworkCatalogEntry.runtimeInstance` | `entry.runtimeInstance?.id`, `.name`, `.protocolMajor`, `.nodeID`, `.runtimeKind`, `.runtimeVersion`, `.launchFingerprint`, `.health`, `.rawCapabilities`. The property that was `runtimeInstanceID` is `id`. |
| `GnosticTimelineObject` (class) | `TimelineSnapshot`, from `NetworkCatalogEntry.timeline` | `entry.timeline?.id`, `.title`, `.isArchived`, `.isPrivate`, `.runtimeInstanceID`, `.attachedWorkspaceIDs`, `.nodeID`, `.createdAt`, `.updatedAt`, and `.status` (a `TimelineStatus`). The Timeline identifier was `objectId`; it is `id`. |
| `GnosticWorkspaceObject` (class) | `NetworkWorkspaceDescriptor`, from `NetworkCatalogEntry.workspace`. The type is unchanged and was already an immutable value. | `uri`, `isAvailable`, `trustLevel`, `status`, `effectiveStatus`, `tools`, `toolsComplete`, `createdAt` read as before. The Workspace identifier was `objectId`; it is `id`. |
| `GnosticWorkspaceToolObject` (class) | `WorkspaceToolSnapshot`, from `NetworkCatalogEntry.workspaceToolSnapshot` | `workspaceID`, `page`, `schemaTruncated`, `protocolMajor`, and `tool` (a `GnosticWorkspaceTool`: `id`, `name`, `toolDescription`, `parametersSchema`, `usageExample`, `requiresPermission`). `toolID` is `tool.id`, `toolName` is `tool.name`. `NetworkCatalogEntry.workspaceTool` is unchanged. |
| `CoatyObject`, `CoatyUUID`, `CoreType` | Not in a stable product. They are in `GnosticCore`. | Read `NetworkCatalogEntry.objectID` (a `UUID`) and the snapshots. Code that builds an object to advertise it is a Node and imports `GnosticCore`. |
| `GnosticRuntimeInstanceHealth` | Unchanged, now declared beside `RuntimeInstanceSnapshot`. | None. |

`NetworkCatalogEntry.knownProperties` and `dynamicProperties` still hold the
raw JSON fields. The `runtimeInstance`, `timeline`, and `workspaceToolSnapshot`
properties are `nil` for another object type, for a payload that does not
decode, and for an incompatible protocol major. The `NetworkCatalogEntry`
initializer gains three optional parameters that default to `nil`.

**The wire format is unchanged.** The snapshots are not `Codable`. The four
`Gnostic*Object` classes keep their `CodingKeys`, their `encode(to:)`, and their
`init(from:)`; only the module changed. `ProjectionWireGoldenTests` holds the
bytes that the classes produced on `origin/main` at `5d7e37b`, before the move,
and requires the moved classes to encode the same bytes with sorted keys. It also
decodes each golden payload, encodes it again, and compares. It then ingests
each payload into `NetworkCatalog` and compares the snapshot's fields with the
values that produced the bytes. `TimelineJournalGoldenTests` is untouched.

**Reference types that stay public.** Five `@MainActor final` service handles
are the only public classes. Each has no settable public property, and actor
isolation makes its `Sendable` conformance checked rather than unchecked. They
are not data, and a value snapshot cannot replace a client that owns a
connection:

| Class | Product |
| --- | --- |
| `GnosticConsumerSession` | `GnosticClient` |
| `GnosticDiagnosticsClient` | `GnosticClient` |
| `GnosticTimelineClient` | `GnosticClient` |
| `GnosticTurnClient` | `GnosticClient` |
| `GnosticWorkspaceClient` | `GnosticClient` |

`StableSurfaceFitnessTests` and `StableSurfaceSourceFitnessTests` fail on an
`open` declaration, on `@unchecked`, on a public class outside this list, on a
class that is not `final`, on a stored or settable public property, and on any
of the moved transport types in the baselines.

#### Runtime instance requirement

Gnostic defines no capability names (ADR 0020 section 8, owner decision D31 on
[#551](https://github.com/phynics/Gnostic/issues/551), [#723](https://github.com/phynics/Gnostic/issues/723)).
`GnosticCapability` and `InteroperabilityCapability` are removed. A Runtime
instance's own ACP `initialize` capabilities travel verbatim in `rawCapabilities`.

The rule that gated the typed clients is unchanged, and it is now stated
directly: **a provider offers a client operation when it advertises at least one
Runtime instance at the current protocol major.** ACP v2 requires every Runtime
to answer `session/prompt`, and the Node that hosts a Runtime instance owns
Timeline management and diagnostics. A client that finds no Runtime instance
reports it with an error of its own, before any wire call:

| Operation | Failure | Error |
| --- | --- | --- |
| Turn (`run`, `replay`, `cancel`) | The operating Runtime instance of the Timeline is not advertised by the Timeline's provider | `GnosticTurnClientError.runtimeInstanceUnavailable(id)` |
| Timeline update | The operating Runtime instance of the Timeline is not advertised by the Timeline's provider | `GnosticTimelineClientError.runtimeInstanceUnavailable(id)` |
| Timeline create | The Runtime instance is not advertised | `GnosticTimelineClientError.runtimeInstanceUnavailable(id)` (unchanged) |
| Diagnostics node | No provider advertises a Runtime instance, or the pinned provider does not | `GnosticDiagnosticsClientError.nodeUnavailable` |
| Diagnostics Runtime instance | The Runtime instance is not advertised | `GnosticDiagnosticsClientError.runtimeInstanceUnavailable(id)` (unchanged) |
| Diagnostics Timeline | The operating Runtime instance of the Timeline is not advertised by the Timeline's provider | `GnosticDiagnosticsClientError.runtimeInstanceUnavailable(id)` |

A Timeline that names no single operating Runtime instance stays
`timelineUnavailable`. Workspace operations never gated on an instance, and
`GnosticWorkspaceClientError.missingCapability` could not occur; it is removed.
A Node with no configured Runtime instance offers no diagnostics, as before.

The ACP frontend maps the same failures: a Turn on a Timeline whose Runtime
instance is not advertised is `RemoteTurnClientError.runtimeUnavailable`, with
`gnosticCode` `runtimeUnavailable`.

## Runtime boundary

Every Runtime uses ACP v2 JSON-RPC over stdio. A Gnostic Node supervises the
process. The in-repository PositronicKit 7 reference Runtime is a standalone
executable. It does not join Axoloty, connect to MQTT, or link the Gnostic host.
Only that executable may depend on PositronicKit. The host and its test targets
have no direct or transitive PositronicKit dependency.

Gnostic removes the in-process `positronic` and `letta` backend kinds. The
bundled 0.4.2 Positronic backend is not a 0.5.0 host backend. Its replacement is
the standalone ACP Runtime process.

## Timeline and Session behavior

Each Timeline has one owning Node and one authoritative, durable, versioned
journal. The journal stores ordered Gnostic orchestration events and ACP v2
updates exactly as received. For each ACP update it stores the UTF-8 text of the
`session/update` line that the Runtime wrote, as a JSON string, so it keeps
`_meta`, unknown update kinds, extra fields, number text, duplicate keys, key
order, a byte order mark, and a trailing carriage return, and it journals an
update that does not fit its type. The journal does not record a notification
with no usable `sessionId`, a message nested more than 128 levels deep or holding
a NUL byte, or an update without a typed form that names an unknown Session. Each
of those gets a warning in the log, and the line itself fails neither the Turn
nor the connection. Skipping a prompt response or an idle `state_update` can still
end the Turn. The Workspace gateway answers HTTP 400 to a request body past the
same depth or holding a NUL byte. The journal
layout and format version are unchanged. The
Node syncs a Turn admission before it dispatches the prompt. It syncs each event
before forwarding it to subscribers or peers.

Production rebuilds the Timeline and Session projections from the journal. It
does not yet rebuild folded messages or tool calls. The journal records a replay
epoch for each open, and its replay API rejects a cursor from another epoch. No
0.5.0 client path replays a Timeline, so nothing can merge a stale replay. The
Timeline history work (#672) is the first consumer of that API. The journal
truncates an uncommitted torn tail and quarantines a corrupt committed prefix
as read-only. Gnostic does not silently fall back to an in-memory record when
it cannot write the journal. The separate Turn event log remains digest-only.

A Turn on a quarantined Timeline fails before Gnostic sends a prompt. The
failure has reason code `timelineQuarantined`, status 423, and is not
retryable. A direct Turn call returns that reason code. A client of
`gnostic acp` receives JSON-RPC error `-32001` with data
`{"gnosticCode":"timelineQuarantined"}`; the data code tells it apart from
`timelineBusy`. The message is fixed and names no path,
frame, or Turn content. `gnostic inspect timeline` reports `journal  quarantined
read-only` in text, and a `journal` object with state `quarantined` in
`--format json`.

Gnostic resumes a Session only on the same Runtime instance and with the
original `cwd`. An ambiguous resume result is neither a confirmed loss nor a
successful resume. Gnostic does not send a new prompt while Session state is
ambiguous.

Changing the Project `cwd` creates a new Session record on the same Timeline.
Gnostic does not claim that the new Session retained the previous model
reasoning. v0.5 does not seed another Runtime from Timeline history or promise
cross-Runtime context handoff.

## Project and Workspace access

A Project supplies the Session `cwd`. v0.5 supports an operator-selected local
directory and a Gnostic-managed scratch directory. A Project is separate from
an attached Workspace.

The Timeline manifest may set `project` to `{"kind":"local","path":"/work/repository"}`
or `{"kind":"scratch"}`. The CLI exposes the same choice through
`config timeline add --project-local <path>`, `--project-scratch`, and the
matching `config timeline update` options. Scratch directories use the
`gnostic-scratch-<uuid>` name under the configured `scratchRoot` or system
temporary directory and have owner-only permissions. A Session binding reports
its `cwd` and Project kind, with `contextContinuityGuaranteed: false`; a new
Session after a Project change does not promise prior model reasoning.

Attached Workspaces reach Runtime sessions as tools through the Gnostic MCP
gateway. The gateway checks attachment intent, current effective status,
permission, and tool membership at the Workspace-owning Node. The two-Node
release journey in #552 proves remote Turn routing and a remote Workspace call
through the gateway.

The release `gnostic` build registers one local Workspace kind, `filesystem`.
It serves a manifest-configured root directory through the read-only
`list_directory` and `read_file` tools. Tools cannot resolve outside the root,
including through symlinks, and output is bounded to the wire payload. See the
README for the manifest entry.

Local and scratch Project placement are not filesystem sandboxes. A Runtime
process can access any path allowed to its operating-system user. Gateway
checks do not constrain the Runtime's own filesystem or shell tools. Operating-
system sandboxing is deferred.

## Turn behavior

Gnostic admits at most one active foreground Turn per Timeline. A distinct
Turn submitted while another is active is rejected before Gnostic sends
`session/prompt`. It is not queued, its user message is not inserted, and no
update is published for it. The JSON-RPC error is `-32001`, with message
`Timeline is busy` and data `{"code":"timelineBusy","retryable":true}`. The
same error reaches a client of `gnostic acp` and a Turn that a Node routes to
the Timeline's owner. A direct Turn call fails with reason code `timelineBusy`
and status 409. Different Timelines run in parallel.

An identical retry with the same `clientTurnID` and canonical prompt digest
attaches to the active Turn, or returns the recorded admission or Turn state,
without sending another prompt. A different prompt under the same ID is a
conflict. The digest is the SHA-256 of the RFC 8785 canonical form of the
prompt content together with the ACP version tag, written as lowercase
hexadecimal.

Gnostic journals admission before it dispatches the prompt, and it sends each
admitted prompt at most once. A response that never arrives (a lost connection,
a timeout, or a Node restart) records `insertionUnknown`. Gnostic does not guess
or retry. A retry, including one after a restart, returns that state.

A Turn ends on the next `idle` update after insertion. An omitted stop reason
produces `endedUnspecified`, which reaches the client as an `idle` update
without a stop reason and the journal as the Turn's recorded outcome. An
unanswered permission request receives the v2 `cancelled` outcome and is
recorded as `unavailable`.

Cancellation uses `$/cancel_request` while the prompt awaits insertion. An
error `-32800` answer ends the Turn `cancelled`, not inserted. A success answer
is followed by `session/cancel`. After insertion, cancellation uses
`session/cancel`. A Turn cancelled before dispatch sends no prompt.

A cancelled Turn waits for the Runtime to settle it, so a Runtime that ignores
cancellation cannot hold the Timeline busy for the prompt timeout. The wait has
up to two bounds of 30 seconds each. The first starts at the cancel and bounds
the answer to `$/cancel_request`. If that answer is still missing, the Turn ends
`insertionUnknown`. The second starts when Gnostic sends `session/cancel` and
bounds the Runtime's `idle`. Other updates after a cancel are dropped and do not
end the Turn. If the prompt was inserted and the Runtime reports no `idle` after
`session/cancel`, the Turn ends with a lifecycle failure
(`acpCancellationUnconfirmed`), not `cancelled`, because the Runtime did not
confirm that it stopped. A Runtime that answers the prompt after 29 seconds
therefore still gets 30 seconds to settle. A cancel after insertion starts only
the second bound. A cancelled Turn ends within 60 seconds of the cancel, plus
the time to send `session/cancel`. Both endings retire the Runtime connection,
so the next Turn does not start beside work that may still run. Retiring the
connection also ends the active Turns of the Runtime's other Timelines as
`cancelled`, as every Runtime retirement does.

A Turn that is not cancelled and reports no `idle` within the prompt timeout
ends with a lifecycle failure (`acpTurnStopped`) and retires the connection in
the same way.

### Observe a Turn and reconnect

After a broker connection is lost, a running Node retries with bounded backoff
until it reconnects or shuts down. It logs the loss and recovery, clears stale
peer catalog entries, republishes its current objects, and discovers peers again.
A broker outage does not cancel an admitted Turn: the owner can finish and
journal it while observers are disconnected. After reconnecting, use the same
Turn ID to retrieve its outcome; retrying does not execute it again.

Shutdown during a reconnect is bounded, not exact. `stopAndWait()` returns within
10 seconds even if a call into the transport never returns. It waits up to 5
seconds for an active reconnect attempt and keeps closing the transport while it
waits. A reconnect attempt or an MQTT connection that is still in flight can
outlive `stopAndWait()`. The attempt then closes the transport when it returns,
and a connect slower than one second after that may stay open until the broker
connection timeout. This is an accepted limit for rc.1. The upstream fix, a
cancellable reconnect and a transport close barrier, is tracked in
[phynics/axoloty#1076](https://github.com/phynics/axoloty/issues/1076).

A consumer observes a Turn in two ways. The live stream is fast and lossy. Replay
is the record. The recipe below combines them without skipping or repeating an
update. Retention can still cut text, and a cut ends in `…[truncated]`.

#### What the live stream says

`GnosticTurnClient.updates(for:timelineID:providerID:)` returns an
`AsyncThrowingStream<TurnUpdate, any Error>`, and the errors it throws are
`GnosticTurnClientError`. Its two endings mean different things:

- **It finishes normally only after it yields the Turn's terminal update.** This
  is the one live signal that the Turn ended.
- **It throws when observation is lost.** The Timeline owner left the network,
  and the catalog evicted it: the error is
  `callFailed(reasonCode: "providerOffline", statusCode: 503, retryable: true)`,
  the same error that `run`, `cancel`, and `replay` throw for that eviction. The
  observed transport ended before a terminal update: the error is
  `callFailed(reasonCode: "observationEnded", statusCode: 503, retryable: true)`.

On the wire, a routing Node that loses the owner publishes a terminal update with
sequence 0, which no real update uses. `GnosticTurnClient.updates` throws it as a
lost observation, with the update's reason code. A consumer that reads the channel
directly must do the same.

A stream can also stay open with no update and no error, for example when a buffer
dropped the terminal update or the transport stopped without ending it. Use a
bounded wait, and replay when it expires.

A thrown error is not a `TurnUpdate`. It has no sequence, so it cannot move a
replay cursor. It also does not say the Turn ended: the owner can still run the
Turn after the consumer lost sight of it. Before #718 the stream yielded a
synthetic terminal update with sequence `last + 1` and `reasonCode`
`providerOffline`. A consumer that saved that sequence skipped the real update
with the same number on replay, and it read a lost observation as a Turn end.

The stream is bounded and latest-biased. Under backpressure it drops the oldest
pending update, so a live update can be missing. A sequence gap is the signal to
replay.

#### What replay says

`replay(timelineID:clientTurnID:message:afterSequence:providerID:)` returns the
retained updates with a sequence greater than `afterSequence`, in order, up to
the wire payload bound. Read the `TurnReplay` fields this way:

| Field | Meaning |
| --- | --- |
| `updates` | The next page of retained updates. |
| `nextSequence` | `nil` on the last page. When another page remains, it is the **last sequence in this page**, not the next event number. Pass it unchanged as `afterSequence`. Do not add one. |
| `terminal` | The Turn reached its terminal update. It can be `true` while pages remain. Drain every page before you conclude. |
| `compacted` | `true` when retention has removed or folded updates and `afterSequence` is below the first retained sequence. It can be true when only thoughts were dropped. It can be false after an interior thought was dropped, when `afterSequence` is not below the first retained sequence. An `assistant_text_snapshot`, when present, replaces accumulated assistant text; the flag alone does not prove completeness. |
| `conflict` | Always `false` through `GnosticTurnClient`. A `message` that doesn't match the Turn recorded under that `clientTurnID` throws `callFailed` with `reasonCode` `turnConflict` and status 409 instead. Do not retry it with the same `clientTurnID`. |

Text that ends in `…[truncated]` was cut by retention or a size bound. The
journal keeps the full text. Treat the text as incomplete.

#### Thoughts and plans

A Turn update also carries the Runtime's thoughts and plans (owner decision D32).
They are separate from the assistant text. `TurnTranscript.assistantText`, the
Turn's result and `carriesAssistantText` never include them.

| Kind | Payload | Consumer rule |
| --- | --- | --- |
| `thought` | `text`, in pieces of at most 800 bytes like assistant text, from ACP `agent_thought_chunk`. | Append the pieces in order. They assemble to the Runtime's thought. |
| `plan` | `plan`: a `TurnPlan` with `planID`, `entries` (`content`, `priority`, `status`) and `truncated`, from ACP `plan_update` with `type` `items`. | Replace the plan with the same `planID`. Never append. |

A plan is a structured value and not text, because each plan update holds the
whole plan and replaces the last one. A client that appended a text form would
duplicate every step. An entry's `content` is at most 120 bytes. A plan keeps at
most 32 entries, and fewer when they do not fit one update (about 1,200 bytes). A
plan over the bound loses its trailing entries and sets `truncated`, so a client
never receives a partial plan as a whole one. The entry content ends in
`…[truncated]` when cut. The journal keeps the whole plan.

Usage, `_meta`, unknown update kinds, whole-message `agent_thought` upserts and
plan types other than `items` stay in the journal and out of the Turn update.

`gnostic acp` renders a `thought` as an `agent_thought_chunk` and a `plan` as an
ACP v2 `plan_update` with `type` `items`. A plan that lost entries ends in an entry
with the content `…[truncated]`, priority `low` and status `pending`, and carries
`_meta.truncated`.

Retention treats them differently from assistant text:

- A snapshot (`assistant_text_snapshot`) holds assistant text only. Retention
  drops the thoughts it folds, so a compacted replay returns only the thoughts that
  are still retained, and the snapshot never contains thought text. The journal
  keeps every thought.
- A snapshot keeps the latest plan for each plan ID in `plans`. A later `plan`
  update replaces it.
- Thoughts count toward the 1,024 update and 1 MiB retention bounds, and retention
  drops them first, oldest first, before it folds any assistant text. When a plan
  ID exceeds the bound, Gnostic retains a prefix and a SHA-256 digest of the
  original ID to reduce collisions; this does not guarantee uniqueness against
  unchanged IDs.
- `gnostic acp` counts only assistant text when it trims a snapshot for a client that
  already holds part of it, so thoughts a client received never shift that offset.

A stored Turn event log written before this change still loads: an update without
`plan` or `plans` decodes with no plan, and an update with them encodes the same
as before when it has none. A reader that predates `thought` and `plan` decodes
them with `updateKind` equal to `nil`, because `kind` is a string, and it ignores
the `plan` field. Handle an unknown kind with a `default` branch.

#### Recipe

1. **Retain** the Timeline ID, the provider ID of the last owner, the client Turn
   ID, the prompt (when you pass `message` for conflict detection), and the
   cursor. The cursor is the highest sequence of a `TurnUpdate` you processed,
   from the live stream or from replay. Never take it from an error.
2. **Replace the session.** A `GnosticConsumerSession` is single-use. After a
   thrown `providerOffline` or `observationEnded`, or after a failed call, call
   `stop()` and create a new session, start it, and create new clients from it.
3. **Rediscover.** Call `discover()`. A restarted owner has a new provider ID, so
   do not reuse the old one. Pass `providerID: nil` and let the client resolve
   the Timeline's provider, or read it from `networkObjects()`. Retry while the
   Timeline is `timelineUnavailable`. A Timeline that two providers advertise is
   `timelineAmbiguous`.
4. **Subscribe before you replay.** Call `updates(for:timelineID:providerID:)` on
   the new client first, and buffer what it yields. An update that arrives
   between the replay and a later subscription is otherwise lost.
5. **Replay from the cursor and drain the pages.** Call `replay` with
   `afterSequence: cursor`. While `nextSequence` is not `nil`, call again with
   `afterSequence: nextSequence`. Drain even when `terminal` is `true`.
6. **Apply in order, and never move the cursor past a gap.** Drop a live or
   replayed update whose sequence is at or below the cursor. Apply a buffered live
   update and advance the cursor only when its sequence is `cursor + 1`. If the
   buffer skips a sequence, keep the later updates buffered, leave the cursor where
   it is, and replay from it: replay returns only sequences above `afterSequence`,
   so a cursor moved past a gap loses that update for good. Replay may itself jump
   a sequence, because retention folds older updates into a snapshot, so apply
   what replay returns as it comes. A snapshot replaces the text you accumulated
   for the updates it covers, and it takes precedence over a buffered live update
   with the same sequence.
7. **Decide.** The Turn ended when you processed a terminal update, live or
   replayed. An error, an empty replay, or a missing owner does not prove it.
   Retry a bounded number of times. To attach to a Turn that is still running,
   call `run` again with the same `clientTurnID` and the same prompt. That is an
   identical retry. It does not send the prompt again.

`gnostic acp` follows the same rule. It delivers a live update only when its
sequence is the next one it expects, and it fills any gap from replay. A lost
observation never advances its cursor, and a failed call returns the original
failure to the ACP client.

### Accepted limits

- Gnostic sends `session/prompt` right after a confirmed `session/resume`. It
  does not wait for an observed `idle` update first. ADR 0019 section 2 still
  requires that observation. ADR 0021 supersedes only the queue and the
  quiet-period inference, because silence does not prove `idle`, so this
  departs from ADR 0019 section 2. Architecture exception `GNO-EXC-0003`
  (issue #687) records the departure. A Session whose resume Gnostic cannot
  confirm is blocked instead of prompted, so an unconfirmed state is never
  guessed.
- `gnostic acp` ends a cancelled prompt with `idle` and stop reason `cancelled`
  as soon as the client cancels. It does not wait for the Node's outcome for the
  Turn. When the Runtime never confirms the cancel, the Node records
  `insertionUnknown` or a lifecycle failure, and a later retry of the same
  `clientTurnID` returns that recorded failure (`invalidState` for a lifecycle
  failure). The live `cancelled` and the replayed failure then disagree. The
  Node's record is the authoritative one. Aligning the live path means holding
  the client's prompt response until the Node settles the Turn, which changes
  when a cancelled prompt returns.
- A client that starts its next prompt as soon as it reads a streamed terminal
  update can briefly receive a retryable `timelineBusy`. The Timeline's slot
  releases after Gnostic publishes that update. Retrying the same request
  succeeds once the slot is free.
- A transport failure before Gnostic finishes sending `session/prompt` is
  recorded as `insertionUnknown`. Gnostic cannot tell a prompt that never left
  from one the Runtime received, so it records the conservative state and never
  sends the prompt again.
- Live and replayed Turn updates carry text in pieces of at most 800 bytes. A
  longer Runtime message arrives as several in-order updates that assemble to
  the journaled text, and no piece splits a Unicode scalar. Retention keeps each
  Turn's updates up to 1,024 updates or 1 MiB. Beyond that, a replay receives one
  snapshot of the older text, at most 800 bytes, ending in `…[truncated]`. Tool
  state content is limited to 256 bytes and ends in the same marker when cut. The
  journal keeps the full text in both cases. `gnostic acp` fills live gaps from
  replay. While replay fails, it holds later updates and retries. If replay still
  fails when the Turn completes, it sends the marker, because text may be missing.

### Storage effect

The admission digest changed from FNV-1a to SHA-256, and the admission records
the ACP version tag instead of `legacy-text-v1`. The Timeline journal keeps
format version 1, because no released build wrote version 1 and its frame did
not change. A journal that a pre-release 0.5.0 development build wrote fails
validation when Gnostic opens it, because its admission digests do not match,
and the Timeline is quarantined read-only. The
Turn event log stores the digest as a string instead of a number, and
`gnostic turn-log` reports it the same way. Discard development journals and
Turn event logs from before this change.
