# Gnostic 0.5.0 compatibility

**Status: in development (unreleased).** Gnostic 0.5.0 is the first supported
line and the source- and wire-breaking minor release after [0.4.2](0.4.2.md).
This declaration records the target contract. The final release declaration
will be checked against the built products and the migration tool before the
0.5.0 tag.

The binding architecture decision is [ADR 0021](../Architecture/ADRs/0021-gnostic-v0-5-architecture-reconciliation.md).
The release gates are tracked by [#551](https://github.com/phynics/Gnostic/issues/551)
and [#602](https://github.com/phynics/Gnostic/issues/602).

## Package and protocol

- Package version: `0.5.0`.
- Protocol major: `3`. This is one breaking increment from protocol major 2.
  A 0.4.2 peer does not interoperate with a 0.5.0 peer.
- The v0.5 operator configuration uses the Runtime, Timeline, Session, and
  Project model. A pre-v0.5 manifest v2 file is an input to the explicit
  migration tool in #642. Schema-v1 migration remains removed under ADR 0003.
- Gnostic accepts ACP v2 only. ACP v1 clients and Runtimes are unsupported.
- ACP v2 support is an opt-in preview behind explicit configuration. It is
  outside the 0.5.x stability promise until ACP v2 stabilizes.

## Stable products

The stable Swift products planned for 0.5.0 are `GnosticProtocol` and
`GnosticClient`. `make verify` runs `make api-check`, which fails on any
unreviewed change to their public API against a baseline the compiler wrote
([`API/`](API/README.md), #676). The 0.4.2 to 0.5.0 differences are recorded,
without gating, in [the API diff](0.4.2-to-0.5.0-api-diff.md). ACP v2 transport
remains preview even when Gnostic's own protocol and consumer clients are
stable.
`GnosticACPWire` is a separate preview product used by ACP Runtime executables.
Its symbols do not enter the 0.5.x stability promise.

### Stable surface names

`GnosticProtocol` and `GnosticClient` name no Ascendant, and no `GnosticCore`
type appears in a `GnosticClient` public signature (owner decisions D13, D17,
D18, and D19 on #551; issue #675). `StableSurfaceFitnessTests` scans both
targets and fails on a declaration that says Ascendant or on a `GnosticCore`
type in a public client signature.

- **Turn types are `Turn*`.** The types that were `Ascendant*` and `Timeline*`
  Turn names are `Turn*`, and they live in `GnosticProtocol`.
- **The Runtime instance is the only identity projection.**
  `GnosticAscendantObject` and the `me.atkn.gnostic.Ascendant` object type are
  deleted. A Node advertises a `GnosticRuntimeInstanceObject` for each
  configured instance as soon as it starts, so a client can address the
  instance before its Runtime connects. After the Runtime answers ACP
  `initialize`, the advertisement carries the version, launch fingerprint, and
  capabilities from that answer.
- **`GnosticProtocol` no longer re-exports ACP names.** The 87 `ACP*`
  typealiases are removed. Code that names an ACP wire type imports
  `GnosticACPWire`, which is a preview product outside the 0.5.x promise.
  Public `GnosticProtocol` signatures that name an ACP wire type still use that
  preview type: `GnosticRuntimeInstanceObject.rawCapabilities`,
  `TurnSessionUpdate.update`, and `TurnTerminalOutcome.from(stopReason:)`,
  which takes an `ACPStopReason`. The API baseline records all three. The
  stable surface review (R2) decides whether they stay; the baseline change
  that removes or replaces them is a review-required API change.
- **Deliberate exceptions: none.** Decision D20 keeps the CLI `ascendant`
  commands and `NodeManifest.Ascendant` (the `ascendants` manifest key) until
  after rc.1. Neither is in a stable product.

#### Diagnostics and capability gating

A Runtime instance advertises no capability list. It provides the names in
`GnosticCapability.providedByRuntimeInstance` by being advertised:

| Capability | Why an advertised Runtime instance provides it |
| --- | --- |
| `textTurnInput` | ACP v2 requires `session/prompt`. |
| `timelineManagement` | The Node that hosts the instance owns Timeline creation and renaming. |
| `diagnostics` | The Node that hosts the instance serves payload-free diagnostics. |

The rule: **a provider offers diagnostics when it advertises at least one
Runtime instance at the current protocol major.** A Runtime-instance diagnostics
call needs that instance to be advertised. A Timeline diagnostics call needs the
Timeline to name its operating instance (`runtimeInstanceID`) and the
Timeline's provider to advertise that instance. When no provider advertises a
Runtime instance, node diagnostics fail with `missingCapability` before any
wire call. A Node with no configured Runtime instance offers no diagnostics, as
before, because the old Ascendant projection carried the capability. A Turn or
Timeline-management call uses the same check for `textTurnInput` and
`timelineManagement`. A name outside the table, such as `workspaceAttachment`,
is never provided and fails with `missingCapability`.

## Runtime boundary

Every Runtime uses ACP v2 JSON-RPC over stdio. A Gnostic Node supervises the
process. The in-repository PositronicKit 7 reference Runtime is a standalone
executable. It does not join Axoloty, connect to MQTT, or link the Gnostic host.
Only that executable may depend on PositronicKit. The host and its test targets
have no direct or transitive PositronicKit dependency.

Gnostic removes the in-process `positronic` and `letta` backend kinds. The
bundled 0.4.2 Positronic backend is not a 0.5.0 host backend. Its replacement is
the standalone ACP Runtime process.

## Timeline and Session behavior

Each Timeline has one owning Node and one authoritative, durable, versioned
journal. The journal stores ordered Gnostic orchestration events and ACP v2
updates exactly as received, including `_meta` and unknown update kinds. The
Node syncs a Turn admission before it dispatches the prompt. It syncs each event
before forwarding it to subscribers or peers.

Production rebuilds the Timeline and Session projections from the journal. It
does not yet rebuild folded messages or tool calls. The journal records a replay
epoch for each open, and its replay API rejects a cursor from another epoch. No
0.5.0 client path replays a Timeline, so nothing can merge a stale replay. The
Timeline history work (#672) is the first consumer of that API. The journal
truncates an uncommitted torn tail and quarantines a corrupt committed prefix
as read-only. Gnostic does not silently fall back to an in-memory record when
it cannot write the journal. The separate Turn event log remains digest-only.

A Turn on a quarantined Timeline fails before Gnostic sends a prompt. The
failure has reason code `timelineQuarantined`, status 423, and is not
retryable. A direct Turn call returns that reason code. A client of
`gnostic acp` receives JSON-RPC error `-32001` with data
`{"gnosticCode":"timelineQuarantined"}`; the data code tells it apart from
`timelineBusy`. The message is fixed and names no path,
frame, or Turn content. `gnostic inspect timeline` reports `journal  quarantined
read-only` in text, and a `journal` object with state `quarantined` in
`--format json`.

Gnostic resumes a Session only on the same Runtime instance and with the
original `cwd`. An ambiguous resume result is neither a confirmed loss nor a
successful resume. Gnostic does not send a new prompt while Session state is
ambiguous.

Changing the Project `cwd` creates a new Session record on the same Timeline.
Gnostic does not claim that the new Session retained the previous model
reasoning. v0.5 does not seed another Runtime from Timeline history or promise
cross-Runtime context handoff.

## Project and Workspace access

A Project supplies the Session `cwd`. v0.5 supports an operator-selected local
directory and a Gnostic-managed scratch directory. A Project is separate from
an attached Workspace.

The Timeline manifest may set `project` to `{"kind":"local","path":"/work/repository"}`
or `{"kind":"scratch"}`. The CLI exposes the same choice through
`config timeline add --project-local <path>`, `--project-scratch`, and the
matching `config timeline update` options. Scratch directories use the
`gnostic-scratch-<uuid>` name under the configured `scratchRoot` or system
temporary directory and have owner-only permissions. A Session binding reports
its `cwd` and Project kind, with `contextContinuityGuaranteed: false`; a new
Session after a Project change does not promise prior model reasoning.

Attached Workspaces reach Runtime sessions as tools through the Gnostic MCP
gateway. The gateway checks attachment intent, current effective status,
permission, and tool membership at the Workspace-owning Node. The two-Node
release journey in #552 proves remote Turn routing and a remote Workspace call
through the gateway.

The release `gnostic` build registers one local Workspace kind, `filesystem`.
It serves a manifest-configured root directory through the read-only
`list_directory` and `read_file` tools. Tools cannot resolve outside the root,
including through symlinks, and output is bounded to the wire payload. See the
README for the manifest entry.

Local and scratch Project placement are not filesystem sandboxes. A Runtime
process can access any path allowed to its operating-system user. Gateway
checks do not constrain the Runtime's own filesystem or shell tools. Operating-
system sandboxing is deferred.

## Turn behavior

Gnostic admits at most one active foreground Turn per Timeline. A distinct
Turn submitted while another is active is rejected before Gnostic sends
`session/prompt`. It is not queued, its user message is not inserted, and no
update is published for it. The JSON-RPC error is `-32001`, with message
`Timeline is busy` and data `{"code":"timelineBusy","retryable":true}`. The
same error reaches a client of `gnostic acp` and a Turn that a Node routes to
the Timeline's owner. A direct Turn call fails with reason code `timelineBusy`
and status 409. Different Timelines run in parallel.

An identical retry with the same `clientTurnID` and canonical prompt digest
attaches to the active Turn, or returns the recorded admission or Turn state,
without sending another prompt. A different prompt under the same ID is a
conflict. The digest is the SHA-256 of the RFC 8785 canonical form of the
prompt content together with the ACP version tag, written as lowercase
hexadecimal.

Gnostic journals admission before it dispatches the prompt, and it sends each
admitted prompt at most once. A response that never arrives (a lost connection,
a timeout, or a Node restart) records `insertionUnknown`. Gnostic does not guess
or retry. A retry, including one after a restart, returns that state.

A Turn ends on the next `idle` update after insertion. An omitted stop reason
produces `endedUnspecified`, which reaches the client as an `idle` update
without a stop reason and the journal as the Turn's recorded outcome. An
unanswered permission request receives the v2 `cancelled` outcome and is
recorded as `unavailable`.

Cancellation uses `$/cancel_request` while the prompt awaits insertion. An
error `-32800` answer ends the Turn `cancelled`, not inserted. A success answer
is followed by `session/cancel`. After insertion, cancellation uses
`session/cancel`. A Turn cancelled before dispatch sends no prompt.

A cancelled Turn waits for the Runtime to settle it, so a Runtime that ignores
cancellation cannot hold the Timeline busy for the prompt timeout. The wait has
up to two bounds of 30 seconds each. The first starts at the cancel and bounds
the answer to `$/cancel_request`. If that answer is still missing, the Turn ends
`insertionUnknown`. The second starts when Gnostic sends `session/cancel` and
bounds the Runtime's `idle`. Other updates after a cancel are dropped and do not
end the Turn. If the prompt was inserted and the Runtime reports no `idle` after
`session/cancel`, the Turn ends with a lifecycle failure
(`acpCancellationUnconfirmed`), not `cancelled`, because the Runtime did not
confirm that it stopped. A Runtime that answers the prompt after 29 seconds
therefore still gets 30 seconds to settle. A cancel after insertion starts only
the second bound. A cancelled Turn ends within 60 seconds of the cancel, plus
the time to send `session/cancel`. Both endings retire the Runtime connection,
so the next Turn does not start beside work that may still run. Retiring the
connection also ends the active Turns of the Runtime's other Timelines as
`cancelled`, as every Runtime retirement does.

A Turn that is not cancelled and reports no `idle` within the prompt timeout
ends with a lifecycle failure (`acpTurnStopped`) and retires the connection in
the same way.

### Accepted limits

- Gnostic sends `session/prompt` right after a confirmed `session/resume`. It
  does not wait for an observed `idle` update first. ADR 0019 section 2 still
  requires that observation. ADR 0021 supersedes only the queue and the
  quiet-period inference, because silence does not prove `idle`, so this
  departs from ADR 0019 section 2. Architecture exception `GNO-EXC-0003`
  (issue #687) records the departure. A Session whose resume Gnostic cannot
  confirm is blocked instead of prompted, so an unconfirmed state is never
  guessed.
- `gnostic acp` ends a cancelled prompt with `idle` and stop reason `cancelled`
  as soon as the client cancels. It does not wait for the Node's outcome for the
  Turn. When the Runtime never confirms the cancel, the Node records
  `insertionUnknown` or a lifecycle failure, and a later retry of the same
  `clientTurnID` returns that recorded failure (`invalidState` for a lifecycle
  failure). The live `cancelled` and the replayed failure then disagree. The
  Node's record is the authoritative one. Aligning the live path means holding
  the client's prompt response until the Node settles the Turn, which changes
  when a cancelled prompt returns.
- A client that starts its next prompt as soon as it reads a streamed terminal
  update can briefly receive a retryable `timelineBusy`. The Timeline's slot
  releases after Gnostic publishes that update. Retrying the same request
  succeeds once the slot is free.
- A transport failure before Gnostic finishes sending `session/prompt` is
  recorded as `insertionUnknown`. Gnostic cannot tell a prompt that never left
  from one the Runtime received, so it records the conservative state and never
  sends the prompt again.
- Live and replayed Turn updates carry text in pieces of at most 800 bytes. A
  longer Runtime message arrives as several in-order updates that assemble to
  the journaled text, and no piece splits a Unicode scalar. Retention keeps each
  Turn's updates up to 1,024 updates or 1 MiB. Beyond that, a replay receives one
  snapshot of the older text, at most 800 bytes, ending in `…[truncated]`. Tool
  state content is limited to 256 bytes and ends in the same marker when cut. The
  journal keeps the full text in both cases. `gnostic acp` fills live gaps from
  replay. While replay fails, it holds later updates and retries. If replay still
  fails when the Turn completes, it sends the marker, because text may be missing.

### Storage effect

The admission digest changed from FNV-1a to SHA-256, and the admission records
the ACP version tag instead of `legacy-text-v1`. The Timeline journal keeps
format version 1, because no released build wrote version 1 and its frame did
not change. A journal that a pre-release 0.5.0 development build wrote fails
validation when Gnostic opens it, because its admission digests do not match,
and the Timeline is quarantined read-only. The
Turn event log stores the digest as a string instead of a number, and
`gnostic turn-log` reports it the same way. Discard development journals and
Turn event logs from before this change.

## Operator migration and historical data

The #642 migration tool accepts the immediate pre-v0.5 schema-v2 manifest. It
validates the input, shows a structured diff in `--dry-run` mode, and creates a
timestamped backup before it changes the source. It preserves stable Node,
Timeline, and Workspace IDs and labels. It reports removed or ambiguous
in-process backend configurations instead of guessing.

The migration changes operator configuration only. Gnostic does not convert
old Turn event logs, Timeline databases, Runtime Sessions, or experiment traces.
Operators keep those files; Gnostic does not silently delete them. v0.5 does not
claim that it can read or resume that historical execution state.

See [Operator configuration migration](Configuration-Migration.md) for preview,
backup, apply, and rollback commands.

## Removed since 0.4.2

- The Ascendant primitive, Ascendant operations, and Gnostic-defined
  interoperability capability set. Clients create Timelines and select Runtime
  instances instead. No Agent primitive replaces Ascendant.
- The in-process `positronic` and `letta` backend kinds and host PositronicKit
  composition.
- ACP v1 negotiation, translation, and compatibility adapters.
- The Timeline-owned Turn envelope, coordinator, and providers
  (`me.atkn.gnostic.timeline.turn*` and `me.atkn.gnostic.timeline.permission*`).
  No Node answered those operations. The live Turn and permission operations
  use the `me.atkn.gnostic.turn*` and `me.atkn.gnostic.permission*` names
  (see [Stable surface names](#stable-surface-names)).
- Native Runtime special Nodes and any Runtime process that joins Axoloty or
  MQTT to execute a local ACP session.
- Automatic cross-Runtime Timeline seeding and claims of model-context
  continuity after a Project change.

The previous 0.5.0 draft described the old package split, capability-gated
diagnostics, and in-process backends. ADR 0021 supersedes those unreleased
claims. The 0.3.0 declaration remains the history for the intentional 0.2
protocol break, the removal of Narrative, and the introduction of Atlas; Atlas
is a parked research reference in 0.5.0.

## Release acceptance

The release requires the structural work in #602, configuration migration in
#642, Axoloty alignment and the two-Node integration in #643, and owner review
in #552. The acceptance record includes:

- a successful build and `make verify`;
- `make container-smoke`, `make runner-smoke`, and `make acp-smoke`;
- ACP v1 rejection and ACP v2 preview conformance evidence;
- torn-tail recovery and corruption-quarantine evidence for the Timeline
  journal, and journal-level evidence that a replay cursor from another epoch
  is rejected (no 0.5.0 client path replays a Timeline);
- a two-Node Turn and Workspace journey with Runtime and Axoloty versions;
- the 8-hour release-candidate soak and owner acceptance.

The accepted declaration replaces this target document before the `0.5.0` tag.
