# Gnostic 0.5.0 compatibility

**Status: in development (unreleased).** 0.5.0 is the first supported Gnostic
line ([#551](https://github.com/phynics/Gnostic/issues/551)). This declaration
is completed before the tag. An earlier draft of it was labelled 0.4.3; that
version was never tagged.

0.5.0 is a **minor** release over [0.4.2](0.4.2.md). It is wire-compatible: a
0.4.2 peer and a 0.5.0 peer interoperate for every operation that 0.4.2
already defined. It is **breaking** in three ways, each listed below:

- Swift consumers: public types moved into new library products (see
  [Consumer SDK extraction](#consumer-sdk-extraction) and
  [Positronic backend extraction](#positronic-backend-extraction)). The
  moved types keep their behavior, names, and signatures.
- Swift consumers and operators: deprecated API and one CLI command were
  removed (see [Removed since 0.4.2](#removed-since-042)).
- Operators: schema v1 manifests are no longer migrated (see
  [Package and protocol](#package-and-protocol)).

## Package and protocol

- Package version: `0.5.0`.
- Protocol major: `2`, unchanged from 0.4.0. Manifest v2 remains the accepted
  and written schema.
- **v1 migration is removed** (ADR 0003 amendment). A schema v1 manifest now
  fails with `unsupportedSchemaVersion`, and a pre-manifest flat
  configuration file is reported as malformed. Neither file is rewritten.
  Migrate an older file with Gnostic 0.4.x before upgrading.
- The bundled Ascendant backend kind is still `positronic` and the bundled
  local Workspace kind is still `echo`.

## Dependencies

- PositronicKit `exact: 6.1.0`, which replaces the `6.1.0-rc.1` prerelease pin
  recorded in [0.4.0](0.4.0.md). Before the 0.5.0 tag, Gnostic moves to
  PositronicKit 7.0 with `.upToNextMinor`
  ([#550](https://github.com/phynics/Gnostic/issues/550)).
- Axoloty `exact: 0.7.0`.
- ACP swift-sdk `exact: 0.1.16`, for the external ACP backend.

## New library products

`GnosticProtocol` (wire contract), `GnosticClient` (consumer SDK),
`GnosticPositronicBackend` (bundled backend), `GnosticHost` (the composition
root), `GnosticKit` (experiment kit), `GnosticACPFrontend`,
`GnosticACPAscendant`, `GnosticLettaBackend`, `GnosticPositronicContext`,
`GnosticRLMGuile`, and `GnosticRLMChibi`. Which products carry the 0.5
stability promise is decided under
[#551](https://github.com/phynics/Gnostic/issues/551). Until then, only the
wire protocol, manifest v2, and the `gnostic` command line are covered by this
declaration.

## Additions since 0.4.2

- External ACP agents as an Ascendant backend (`acp-client`, ADR 0011), with
  permission mediation, scoped Turn cancellation, and process ownership.
- Opt-in durable state (ADR 0014, ADR 0015). The state home is the parent
  directory of `--turn-log PATH` when given, else `GNOSTIC_STATE_HOME`. With a
  state home, `gnostic serve` keeps a durable Turn event log and, for
  Ascendants on the bundled `positronic` backend, a file-backed Timeline store
  under `<state home>/timelines`. `gnostic turn-log` inspects the log. With
  neither setting, serve stays process-scoped as in 0.4.2. Both on-disk
  formats are new and will change before the 0.5.0 tag: the Timeline store is
  replaced by PositronicKit's SQLite storage
  ([#550](https://github.com/phynics/Gnostic/issues/550)).
- The module system and console: `gnostic config module`, `gnostic config
  regime show`, `gnostic doctor`, and `--dry-run` on mutating `config`
  subcommands.
- The experiment kit: `gnostic experiment run`, `export`, and `replay`.
- Capability-gated live diagnostics, described below.

## Removed since 0.4.2

- `GnosticWorkspaceProvider` is removed (#560). Hosts use
  `MultiplexedWorkspaceProvider` with `LocalWorkspace` capabilities and its
  required `workspaceStatus` lookup. Supply the Node registry's effective
  status; an absent record refuses invocation. `WorkspaceInvocation` remains
  the shared request type and `GnosticWorkspaceProtocol.invocationOperation`
  names the wire operation.
- CLI: `gnostic config positronic` is removed (#381). Configure a Positronic
  Ascendant with `gnostic config backend set`.
- Configuration: schema v1 manifest decoding, `llmProfiles` inlining, the
  pre-manifest flat-file conversion, and the `_legacyID` cleanup (#381).
- Deprecated Swift API (#381): `AscendantPermissionRequest`,
  `AscendantAdapterRegistry.register(kind:languageModel:)`,
  `WorkspaceAdapterRegistry.register(kind:factory:)`, and the alias spellings
  `BackendConfiguration`, `NodeManifest.Backend`, `JSONValue`, the
  `*Configuration` aliases, `NodeManifestStore`, and `ContextFilter`.
- Unused public declarations (#376): `OrchestrationProjector`,
  `AxolotyWorkspaceFactory`, the orphaned `ServeTrace` lifecycle and operation
  helpers, `NodeRuntime.echoToolID`, `NodeRuntime.attachableWorkspaces`,
  `NodeManifest.defaultManifest`, `NetworkCatalogEntry.workspaceStatus`,
  `NodeRegistry.removeRuntimeTimeline`, and, inside the `GNO-EXC-0001` scope,
  `PayloadCoder`, the `AdvertiseEvent` decoder, and
  `CoatyObjectSnapshot.decodeObject` and `decodePayload`.

## Remote Workspace invocation

The production handler now checks effective Workspace status and the current
tool catalog before executing a remote invocation (#560). An unavailable,
unsupported, or missing registry status returns `409 / workspaceUnavailable`.
A tool absent from `LocalWorkspace.listTools()` returns
`403 / workspaceToolNotAdvertised`, with no execution and no tool identifier
in the failure message. Other invocation errors retain their existing mapping.

Tool queries default an omitted `page` to zero. Pages stay sorted by tool ID,
and a page past the end returns an explicit empty answer. Request and response
shapes and protocol major 2 are unchanged.

## Capability-gated live diagnostics

0.5.0 adds three read-only diagnostics operations and one interoperability
capability:

- `me.atkn.gnostic.diagnostics.node`
- `me.atkn.gnostic.diagnostics.ascendant`
- `me.atkn.gnostic.diagnostics.timeline`
- `me.atkn.gnostic.capability.diagnostics`

The operations return counts, identifiers, backend health, quarantine state,
and Workspace effective status. They never carry a Turn body, a secret value,
or raw wire payload, and they never mutate Node state. A Node advertises the
new capability on its Ascendant projections. A consumer gates every call on
that advertisement, so a Node without the capability degrades with a clear
local failure instead of an unknown-operation error. No protocol major bump is
required: the new capability and operations are additive.

`gnostic inspect` gains four commands that use the new surface:
`gnostic inspect node`, `gnostic inspect ascendant <uuid>`,
`gnostic inspect timeline <uuid>`, and `gnostic inspect events`. Each command
supports `--format json`. The `events` command renders the bounded raw
wire-event stream through the existing consumer facade and renders only the
event envelope and payload byte count, never the payload.

## Consumer SDK extraction

The consumer-facing session and typed clients move from `GnosticCore` to a new
`GnosticClient` library product:

- `GnosticConsumerSession` and its public error type.
- `GnosticTurnClient`, `GnosticTimelineClient`, `GnosticWorkspaceClient`, and
  `GnosticDiagnosticsClient` with their public error types.

Every type keeps its name, behavior, and signature. A consumer adds
`import GnosticClient`; `import GnosticCore` alone no longer publishes the
facade. `GnosticClient` depends on `GnosticProtocol` and `GnosticCore` and
imports no PositronicKit, `PKContracts`, or backend value. The kernel keeps the
shared transport, subscription, and runtime-effect machinery and does not
depend on `GnosticClient`.

## Positronic backend extraction

The bundled Positronic backend moves from `GnosticCore` to a new
`GnosticPositronicBackend` library product:

- `PositronicAscendantAdapter` and the Positronic contribution seam.
- `AxolotyWorkspace` and the Axoloty network Workspace invoker.
- `FileTimelineRuntimeRepository`, `DiscoveredWorkspaceAttachmentService`, and
  `NetworkManagementTools`.
- `AscendantToolApprovalPolicy`, `EchoWorkspace`, and
  `PositronicWorkspaceProjection`.

Every type keeps its name, behavior, and signature. A consumer that named one
of these types through `import GnosticCore` adds
`import GnosticPositronicBackend`. Runtime consumers keep `import GnosticCore`
and compose the backend through `PositronicBackend.register(into:)` or the
`GnosticHost` composition. `GnosticPositronicBackend` depends on `GnosticCore`,
`GnosticProtocol`, Axoloty, PositronicKit, and `PKContracts`. `GnosticCore`
declares no PositronicKit, `PKContracts`, or `PKPrompt` dependency and imports
none, so the kernel is Positronic-free. The bundled Ascendant backend kind
stays `positronic` and the bundled local Workspace kind stays `echo`; a
composition root must install the backend before it builds a Node.

## Carried forward from 0.4.2

The 0.4.2 declaration remains authoritative for the load-time cancellation
shield fix. The 0.4.1 declaration remains authoritative for the
deployment-target fix. The 0.4.0 declaration remains authoritative for the
public consumer clients; its PositronicKit prerelease pin is replaced as
described under [Dependencies](#dependencies). The 0.3.0 declaration remains
authoritative for ACP addressing, manifest v2 behavior, bundled
implementations including the Atlas boundary, the intentional 0.2 protocol
break, and the removal of Narrative and the direct conversational CLI. Its
manifest migration behavior is superseded as described under
[Package and protocol](#package-and-protocol).
